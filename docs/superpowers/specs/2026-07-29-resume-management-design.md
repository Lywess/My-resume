# 多岗位简历管理设计

日期：2026-07-29  
状态：待用户审阅

## 背景与目标

原始简历（`王渊的简历.txt`）信息量大、项目描述偏背景长文，猎头反馈：**职责不清晰、内容过多**。

目标：在本仓库用 Git 管理多岗位简历，按猎头/岗位要求独立修改对应分支，不强制多文件合成。

## 决策摘要

| 项 | 决定 |
|----|------|
| 源格式 | Markdown（`.md`） |
| 结构模式 | 主分支总库 + 岗位分支独立可投递稿 |
| 合成方式 | 不强求从模块拼装；岗位分支各有完整 `resume.md` |
| 首批岗位 | 视觉算法、运动控制、项目管理 |
| 工作经历 | 同一公司在不同分支写成不同侧重的职责表述 |

## 分支与文件

```
main
├── README.md
├── source/original.md          # 从 txt 整理的完整素材（参考/备份）
└── docs/superpowers/specs/...  # 本设计文档

role/vision
└── resume.md                   # 视觉算法可投递稿

role/motion-control
└── resume.md                   # 运动控制可投递稿

role/project-mgmt
└── resume.md                   # 项目管理可投递稿
```

### 日常用法

1. 猎头要求改某岗 → 切换到对应 `role/*` 分支，只改该分支 `resume.md`
2. 其他岗位分支不动
3. `main` 的 `source/original.md` 作原始素材备份；新开岗位时从 `main` 或相近分支拷贝再改

### 暂不做

- Word/PDF 自动导出
- 模块拼装脚本 / YAML 勾选生成
- 质量管理等其它岗位分支（需要时再开）

## 写法规范（解决职责不清、内容过多）

- 工作经历：每段 **3～5 条**，格式为「做了什么 → 用了什么 → 结果是什么」
- 项目：每岗 **3～5 个**；每个项目：1 句描述 + **3～4 条**职责/业绩
- 删除：项目背景长文、目标论述、痛点散文；保留动作与可核验数字
- 优势亮点：每岗 **4 条**，只写该岗相关能力
- 求职意向：与当前分支岗位一致（避免同一稿挂多个无关标题）

## 岗位选材

### `role/vision`（视觉算法 / 机器视觉）

- 经历侧重：图像处理、靶点识别、飞拍、OpenCV/深度学习工程化、渲染相关
- 优先项目：飞拍、极高精度算法、多模型识别、Vmask 图形渲染；点喷除草/自动标定择要；**RTK 多引擎定位**（定位中间件，投自动驾驶视觉/感知时保留）
- 弱化/拿掉：市场/质量信息化长述、WFC 毕设、纯低代码平台、运动主控细节堆砌

### `role/motion-control`（运动控制 / 设备上位机）

- 经历侧重：主控架构、运动平台、IO/激光/联锁、软硬件联调、节拍与同步
- 优先项目：杨泰主控重构、飞拍（相机硬触发与运动同步）、AEB 控制链路、点喷控制/执行层
- 弱化/拿掉：纯信息化、LLM/RAG、**RTK 默认不放**（除非 JD 明确要求导航定位进控制闭环）

### `role/project-mgmt`（项目管理 / 软硬件协同交付）

- 经历侧重：跨子系统推进、需求落地、联调验收、信息化平台负责人视角、进度与质量闭环
- 优先项目：质量管理信息化、市场管理信息化、飞拍（负责人）、杨泰重构（联调交付）、多模型/高精度（工程落地）；RTK 可弱写一条「多引擎框架从架构到落地」
- 弱化/拿掉：算法公式级细节、纯代码实现罗列、毕设

## 专题归类：RTK 多引擎兼容

**不算运动控制代码。**

本质是：定位接收机适配、差分服务抽象、协议解析、配置层——属于**定位中间件 / 嵌入式通信**。

| 岗位 | 处理 |
|------|------|
| 视觉 | 可保留（感知/定位链路） |
| 运动控制 | 默认不放 |
| 项目管理 | 可弱写一条交付视角 |

## 工作经历改写原则

同一段在职经历，三分支写法不同，例如新诺微电子：

- 视觉分支：飞拍、靶点识别、视觉接口、图形渲染等
- 运动控制分支：主控重构、运动/IO/激光模块、设备联调等
- 项目管理分支：多子系统协同、版本交付、信息化项目负责等

超达智能：按真实职责写具体模块，避免空泛「参与训练/调优」；若实质为视觉/定位/嵌入式，写清模块与结果。

## 首次实现范围

1. `main`：`source/original.md`（txt → md 结构化，内容可偏全）+ `README.md`
2. 创建三分支并各写精简 `resume.md`（经历按岗改写 + 项目按上表裁剪）
3. Git 提交仅在用户明确要求时执行

## 成功标准

- 猎头打开任一 `role/*/resume.md` 能在短篇幅内看清「这个人在这个岗做什么」
- 改某一岗不影响其他岗
- 新增岗位成本低：新开 `role/<name>`，复制相近 `resume.md` 再改
